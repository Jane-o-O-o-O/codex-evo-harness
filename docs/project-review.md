# 项目扫描与优化记录

日期：2026-09-22。项目采用 Node.js HTTP 服务、原生 JavaScript 前端、Electron 桌面壳和文件系统存储。扫描覆盖 Trace 发现与归约、查询索引、每日复盘、模型调用、Agent 状态和审批、Harness 修改与回滚、页面交互、桌面启动、Windows 脚本、打包配置及现有测试。

本轮优先处理会导致统计遗漏、刷新变慢、读取失败和并发保存失败的问题。没有调整业务界面布局，也没有改变 Harness 修改所需的逐项审批流程。

## 已落实的修改

| 问题 | 修改 | 验证 |
| --- | --- | --- |
| 每轮扫描重新解析全部 `state.json`；页面和调度器可能同时扫描 | 为每个服务实例缓存摘要，以文件大小、修改时间、状态变更时间和 inode 判断失效；合并并发扫描；删除的目录释放缓存 | 缓存前后结果一致；同大小改写、删除目录、晚到的项目 metadata 均正确刷新 |
| 全量统计和搜索传入 `limit: 10000`，超过列表允许范围后回退成默认 200 条 | 将全量筛选与有上限的列表返回拆开；统计、搜索、反馈及取消回合查询遍历完整作用域 | 1,002 个 Session 中，最旧记录仍可被统计和检索；列表仍遵守返回条数限制 |
| 每次刷新追加相同 Cursor，20 次后挤掉真实历史 | Cursor 历史去重；内容不变时不重写索引；同一目录的并发索引刷新共享任务 | 连续 25 次刷新后，旧 Cursor 仍准确识别新增 Session，索引文件 mtime 不变 |
| 单个损坏的状态文件阻断整个 Agent 索引 | 单独记录坏文件，继续索引正常记录；Dashboard 提示异常数量；下次刷新重试 | 损坏和修复场景通过 |
| 旧索引未检查来源和版本；首条用户摘要未脱敏 | 按根目录及 schema 校验缓存；索引升级到 v3，重新生成脱敏摘要 | 旧 schema 重建、密钥脱敏验证通过 |
| Payload 调用参数可以提高用户配置的字节预算 | 请求限制与配置限制取较小值，并检查实际读取字节数 | 增大参数不能绕过配置；多字节文本按字节计算 |
| Payload 不存在时直接建立读取流，异步错误未处理 | 先打开并校验文件，再发送响应；处理流错误和客户端断开 | 缺失文件返回 404，随后请求仍正常 |
| 快速切换 Trace 或 Payload，旧响应可能覆盖新选择 | 请求序号、当前路由和 DOM 存活检查；刷新完成时保留当前选中的节点 | 浏览器中人为延迟旧 Trace 请求，最新页面保持不变 |
| JSON 临时文件名可能碰撞，Windows 并发 rename 也会冲突 | 提取共用原子 JSON 写入模块；随机临时文件；同一目标文件串行写入并清理临时文件 | 同时提交 32 次写入，最终文件完整，无临时文件残留 |
| 开发依赖锁定了已有修复版本的漏洞包 | 更新 `@xmldom/xmldom` 至 0.8.15、`fast-uri` 至 3.1.8、`js-yaml` 至 4.3.2 | npm 官方 registry 审计的高危依赖项由 5 个降至 2 个 |

新的 `atomic-file.mjs` 已加入 Electron 打包清单及打包清单测试。Trace 索引是可重建缓存，v3 首次运行需要重新读取状态文件；Agent Run、Proposal、Approval 和 Change 的存储 schema 仍为 v2。

## 验证结果

- 修改前：`npm test`，80 项通过。
- 修改后：`npm test`，88 项通过，新增 8 项回归测试。
- 在 Windows、Node.js v24.18.0 上验证；前端脚本通过 `node --check`。
- 浏览器使用仓库示例数据，验证日期到会话、Trace 详情，以及较旧请求延迟返回的场景。
- `npm audit --omit=dev --registry=https://registry.npmjs.org`：生产 npm 依赖零已知漏洞。Electron 虽被列为开发依赖，但会成为桌面应用运行时，不能据此推断桌面安装包没有漏洞。
- 本轮没有运行真实远端模型请求、真实 Harness 修改或 Electron 安装包构建；模型和修改流程通过项目已有的隔离测试验证。

性能对比使用同一进程、同一磁盘上的 200 个模拟 bundle，每个 `state.json` 约 134 KB（示例状态加模拟大字段）。缓存预热后，旧版和新版交替执行 5 次完整发现扫描：

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 中位扫描耗时 | 472.8 ms | 216.3 ms |
| 相对耗时 | 100% | 45.8% |

这是重复扫描的微基准，约提升 2.19 倍；不是首次加载或整页响应的性能承诺。真实收益取决于 bundle 数量、状态文件大小、正在增长的日志和磁盘速度。

## 后续优先项

1. **升级并验证 Electron。** 完整依赖审计仍有 `electron` 和 `extract-zip` 两个高危依赖项。npm 建议升级至 Electron 44.4.3，超出当前 `^37.0.0` 范围。需要覆盖首次设置、IPC、窗口生命周期及 Windows NSIS 安装/卸载后再发布；本轮只更新兼容范围内的依赖。
2. **为归约器增加全局并发上限。** 当前按 bundle 去重，但大量历史 Raw bundle 可能同时启动多个 CLI。应结合归约耗时和机器内存设定并发数，并增加排队状态及停止服务时的清理。
3. **为 Harness 变更增加完整事务互斥。** 本轮串行化的是单文件写入，不是整个“读取—消费审批—修改—验证”事务。多窗口、多请求同时执行变更时，应按目标文件和 Run 加锁，并测试重复提交与冲突回滚。
4. **继续降低大数据量下的扫描和渲染成本。** 当前仍会扫描 manifest、日志尾部及索引文件。下一步可测量后引入增量摘要读取、Session 分页和长调用树的虚拟列表；同时将 `public/app.js` 的路由、数据请求和渲染拆成可独立测试的模块。
